# `/find` 托管 Everything 设计与实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 用 UiPilot 安装并管理的 Everything 1.4 Stable Service、隐藏客户端和 Query2 IPC，替换未完成的 Rust 自研文件索引，同时保持现有 `/find` 交互、响应协议和文件执行安全边界。

**Architecture:** 安装器负责一次 UAC、受管二进制和 Windows Service；UiPilot 用户态进程负责启动专用 Everything 客户端、维护 IPC 消息线程并把查询结果适配为现有 `FileSearchResponse`。迁移期通过 `FileSearchBackend` 隔离旧 `FileIndex` 和新 Everything backend，生产切换验收后删除旧索引。

**Tech Stack:** Rust 1.96、Tauri 2.11、`windows` 0.61、Win32 `WM_COPYDATA`/Query2 IPC、NSIS per-machine、PowerShell、React 19、Vitest 4。

## Global Constraints

- 目标平台仅 Windows x64。
- 基线候选为 Everything `1.4.1.1032 x64 Stable`；Iteration 0 记录 SHA-256 后冻结。
- 不采用 Everything 1.5 Beta，不自动跟随上游版本。
- 安装器采用 NSIS per-machine，一次 UAC；UAC 被拒绝时整次安装取消。
- 使用 UiPilot 专用 instance、Service、pipe、配置和数据库目录，不操作用户自己的 Everything。
- 首版 Service pipe 授权 SYSTEM、Administrators 和首装 credential-owner `service_owner_sid`；OTS 桌面标准用户
  及其他非 Administrators、非 credential-owner 本地账户不支持 `/find`。
- `/find` 只搜索名称和元数据，不搜索文件内容，不开放 Everything 高级语法。
- WebView 不能提交路径、Shell 参数、Everything 表达式、instance 或 pipe。
- 搜索结果最多 200 项，`total` 必须与产品语义一致。
- 日志和验证产物不得包含查询词、文件名、完整路径、用户名或原始 IPC buffer。
- 新旧后端只在开发迁移期并存；生产切换后必须删除旧索引代码与 `rusqlite`。

## 一、决策摘要

### 1. 可行性

方案可行。Everything 已覆盖自研索引中最昂贵的固定卷枚举、USN 增量更新、数据库持久化、恢复和排序能力。
UiPilot 仍需自研的部分收敛为：安装与升级、进程监督、Query2 IPC、查询语义适配、结果令牌和故障体验。

### 2. 生产方案

采用 Rust 原生 Query2 IPC：

```text
NSIS Installer (elevated)
  ├─ deploy pinned Everything.exe
  ├─ install/start UiPilot-owned Everything Service
  └─ write protected ownership manifest

UiPilot.exe (normal user)
  ├─ EverythingRuntimeSupervisor
  ├─ EverythingIpcWorker
  ├─ EverythingFileSearch
  └─ ResultRegistry

Everything.exe -instance UiPilot (hidden user process)
  └─ private service pipe
       └─ UiPilot-owned Everything Service
```

Everything SDK DLL 只在独立 Spike 中作为结果对照，不进入首版生产包。`ES.exe`/CLI 每次启动子进程的
方案不进入 Spike。

### 3. 保留与删除

保留：

- `src/protocol.ts` 的文件搜索协议。
- `/find` React UI、类别、排序、键盘和 stale-response 行为。
- `search_files` Tauri command 的调用形状。
- `ResultRegistry` 的 query token 和 opaque `resultId`。
- `execute_result` 的 Rust 内部文件动作分支。

删除：

- 固定卷扫描、USN watcher、SQLite 索引和 integrity worker。
- FileIndex 的 runtime epoch、pause/clean-close/recovery 状态机。
- `rusqlite` 和只服务于旧索引的 Windows features。
- 旧索引性能与 I/O 证据脚本中不再适用的扫描门禁。

映射到现有前端：`Starting -> building`、`Ready -> ready`、`Partial -> partial`、
`Rebuilding -> rebuilding`、所有 `Unavailable(_) -> unavailable`。

`FileInvalidationReason` 的固定前端映射：`BackendRestarted`、`Rebuilding` -> `rebuilding`；
`RuntimeUnavailable`、`ManifestMismatch`、`OwnerMismatch`、`ProtocolMismatch`、
`RuntimeIdentityExhausted`、`RevisionExhausted` -> `unavailable`。前端只使用固定非敏感文案，不显示路径、SID、
manifest 内容或底层 IPC 数据。

恢复分类同时冻结：`BackendRestarted`、`RuntimeUnavailable`、`Rebuilding` 是 recoverable，ack 后只有 supervisor
重新进入 `Ready` 才允许有界退避 `search_files` bootstrap；`ManifestMismatch`、`OwnerMismatch`、
`ProtocolMismatch`、`RuntimeIdentityExhausted`、`RevisionExhausted` 是当前进程 terminal/sticky，ack 后仍保持
`unavailable`，停止 timer/search/execute 且不得 bootstrap。terminal 原因不允许同进程“重新认证”解除；必须退出
UiPilot，在外部重新安装/修复受管组件后启动新进程，重新建立 manifest/owner/protocol 与 runtime identity 信任域。
该 terminal/recoverable runtime state 由 supervisor/service 全局持有，独立于 invocation、ResultSet 和 tombstone；
hide/show、创建新 invocation 或清理旧 tombstone 均不得重置。

### 2. 后端接口

```rust
pub(crate) trait FileSearchBackend: Send + Sync {
    fn runtime_identity(&self) -> BackendRuntimeIdentity;

    fn search(
        &self,
        query: QuerySpec,
        expected_backend_identity: BackendRuntimeIdentity,
    ) -> Result<AuthenticatedFileSearchBatch, FileSearchError>;

    fn execute(&self, action: &FileResultAction)
        -> Result<FileExecutionOutcome, FileExecutionError>;

    fn shutdown(&self);
}

#[derive(Clone, Copy, Eq, PartialEq)]
pub(crate) struct BackendRuntimeIdentity {
    pub(crate) epoch: u64,
    pub(crate) generation: u64,
}

pub(crate) struct AuthenticatedFileSearchBatch {
    pub(crate) backend_runtime_epoch: u64,
    pub(crate) backend_generation: u64,
    pub(crate) status: FileSearchStatus,
    pub(crate) total: u32,
    pub(crate) items: Vec<AuthenticatedFileSearchItem>,
    pub(crate) fingerprint: ResultFingerprint,
    // No request/result IDs and no revision.
}
```

`BackendRuntimeIdentity::epoch` 和 `generation` 均只能 checked increment。任一字段的下一次递增发生 overflow 时，
supervisor 进入进程生命周期内不可恢复的 `RuntimeIdentityExhausted` terminal state，停止启动、查询和执行并映射
为 `unavailable`；不得回绕、归零或创建复用旧 identity 的新 backend。只有完整退出 UiPilot、销毁内存中的
ResultRegistry/actions 后，新的应用进程才能建立全新的内存 identity domain。单测从
`u64::MAX - 1` 覆盖最后一次成功递增、下一次失败闭合，以及所有旧 action/lease 拒绝执行。

```rust

```

window 层调用 `encode_query2(&EverythingQuerySpec, QueryReplyRoute)` 注入 reply HWND/message；收到
`WM_COPYDATA` 后先验证 source HWND 和 `dwData`，再把 payload 交给
`decode_list2_payload(&[u8])`。payload parser 不生成 query id，并对实际 request flags、sort type、总长度、
item count、字段 offset、UTF-16 终止和整数溢出逐项检查。

Query2 offset 页不是快照。为每个目录条目构造同一规范化 `EntryKey`：版本字节 + 经 handle 认证后的 canonical
absolute full path（统一 namespace/分隔符后，以长度前缀 UTF-16 code units 做 case-sensitive ordinal 比较）+
leaf volume serial + file ID + kind + attributes。对象 identity 相同但 canonical path 不同的 hard links 是不同 entry。
分页采用双遍读取：page size 256、overlap 64；每页校验 total/flags/sort，overlap、dedupe、sentinel、双遍比较和
fingerprint 全部使用 `EntryKey`。仅相邻 overlap 区域中完全相同的 key 可折叠；非 overlap 重复 key、相同 file ID
但路径变化、sentinel 缺失或次序变化均视为漂移。读取完整 cutoff tie group 后，从 offset 0 执行第二遍并要求
有序 entry-key 序列完全相同。

deadline 分两层：每个 Query2 page/request deadline 最多 1 秒，并取 transaction 剩余时间的较小值；一次完整
双遍、tie-group 和最多 2 次整次重试共享 3 秒 transaction deadline，而不是每遍或每页各 3 秒。每遍仍限制
64 页、16,384 个 entry 和 32 MiB。耗尽返回 `ConcurrentMutation`，超限返回 `TieGroupTooLarge`，均不计入
crash-loop。

当前 file ResultSet 必须拥有 server-owned `FileRefreshContext`；WebView 不能在 refresh 请求中提交 query、category
或 sort。`refresh_files` 的首句门禁是 `require_main_window(&window)?`，随后只用 invocation/current request ID 调用
`begin_preserving_refresh`。该方法验证 active invocation、file domain 和 request ID，返回当前集合绑定的 context，
且不修改 `latest_query_sequence`、`current`、requestId 或 resultId。未知字段由 `deny_unknown_fields` 拒绝；无
current 时先检查 invocation-scoped tombstone：active invocation 与 `prior_request_id` 匹配且未确认时必须返回
`Invalidated`，不能返回 `BootstrapRequired`。launcher 先清空 UI，再用同一 request 携带
`acknowledgedInvalidationId`；registry 验证 ID 后消费 tombstone、保存 invocation-scoped
`FileInvalidationAckReceipt`，并返回带 acknowledged ID/recovery 的 `BootstrapRequired`。只有该 invocation 从未
发布过 ResultSet、也没有 tombstone/receipt 的初始无 current 状态可直接返回未确认 ID 的 BootstrapRequired。
旧 invocation 的 tombstone/receipt 对新 show invocation 不可见，并在 invocation ownership
切换时清理；不匹配的旧 request 返回 `Stale`。

backend 在 registry 锁外按 token 内的 `QuerySpec` 和 runtime admission 完成查询、双遍分页、逐组件认证和
fingerprint 构建。`commit_refresh_if_current` 在一个锁临界区内重新验证 result-set generation、domain epoch、
request ID、query key 和旧 backend identity：fingerprint 不变时 IDs/revision/action 完全不变；变化时才分配
新的 registry `result_set_generation`、request/result IDs 并原子替换 ResultSet。registry 不修改 batch/action 的
backend identity。普通 query、hide/domain invalidation 或另一 refresh 已提交都会返回 `Stale`；两个并发 refresh
最多一个可替换当前集合。旧 ID 在提交点之前持续有效；提交前已 resolve 的 `ExecutionLease` 可继续进入 backend
admission，但 runtime identity 已变化时仍失败。

错误分两类：`ConcurrentMutation`、`TieGroupTooLarge`、单次 `Deadline` 是 query-level soft error，只丢 token 并
保留 current；refresh 观察到的 `StaleRuntime`、`Restarted`、`Unavailable`、manifest/owner/protocol mismatch
必须调用 `invalidate_file_domain_if_current(token, observed_backend_identity, reason)`。该原子操作重新验证 token
的 result-set/domain/request/query key 和旧 backend identity；若已被新 query 或新 runtime supersede，只返回
`Stale`，绝不能清空新集合。supervisor 不直接持有或修改 ResultRegistry；它通过 bounded、typed
`FileLifecycleTransition` channel/callback 把 observed backend identity、status 和 reason 交给
`FileSearchService`/command 层的唯一 registry owner。`search_files`、`refresh_files`、`execute_result` 和状态读取
在 main-window/admission gate 后、读取 registry 前先 drain transition。owner 仅对仍匹配 observed identity 的
authoritative transition 执行 invalidation，避免迟到事件回滚较新 runtime。

同一 active invocation 存在 unacked tombstone 时，`ResultRegistry::begin_query` 必须在分配 query token、调用
backend 或修改 current/revision 前返回 typed `InvalidationPending`，携带当前 tombstone payload；普通
`search_files`/new query 不得抢先查询、发布或分配 request/result IDs。前端按与 refresh Invalidated 相同的流程
清空展示并通过 `refresh_files` CAS ack。`execute_result` drain 后若有 tombstone 或无 current，必须拒绝执行；
status command 可返回当前 invalidation/status 但不得消费。只有 current tombstone CAS ack 成功、全局 runtime
admission 为 Ready 且 reason recoverable 后，`begin_query` 才能成功。terminal reason 在任何 invocation 永不允许
begin/publish。

成功失效在清空 current 的同一锁临界区保存 `FileInvalidationTombstone`，再由下一次匹配 prior request 的 refresh
返回 typed `Invalidated { invalidationId, indexRevision, status, reason, revisionExhausted }`。registry 使旧 resolve
stale，并在可递增时 checked increment revision；overflow 时保留最后可表示 revision、设置
`revisionExhausted=true`，仍必须依靠 `Invalidated` kind 可靠清空 UI，而不能等待更大的 revision。launcher 收到
Invalidated 后立即清空 requestId/results/selection、停止执行和 refresh timer，确认 tombstone 后进入状态提示与
退避。launcher 只在不可执行、不可渲染的 `pendingInvalidationAck` 中暂存 prior request ID + current
invalidation ID + reason/recovery class；该记录不能重新授权或显示旧结果。`BootstrapRequired` 只描述 registry
当前没有 ResultSet，不是无条件启动搜索的指令：recoverable 原因在重新 Ready 后执行有界 bootstrap；terminal
原因在当前进程永不 bootstrap。所有 bootstrap（包括首次进入 `/find`、new invocation、ack 后恢复）必须先通过
`FileSearchService::bootstrap_admission()`：仅全局 runtime status 为 `Ready` 且没有 terminal sticky reason 时允许
search；`Starting`/`Rebuilding`/其他 recoverable 状态等待 Ready；terminal 状态直接拒绝。只有存在 current 才调度 refresh。

同一 invocation/prior request 的多次 authoritative transition 合并到一个 tombstone，并以 `invalidation_id` 作为
CAS 版本。完全相同的 transition 不递增 revision、不轮换 ID。status、reason、index revision、
`revision_exhausted`、observed backend identity 或 terminal severity 任一可观察 payload 改变时，原子更新 payload
并生成全新 opaque `invalidation_id`；revision 未 exhausted 时该 accepted non-identical transition checked
increment 一次，已 exhausted 时 revision 保持最后值但仍轮换 ID；
`RuntimeIdentityExhausted`、`RevisionExhausted`、manifest/owner/protocol mismatch 是 terminal/sticky，不得被后续
rebuilding 降级；`revision_exhausted` 使用逻辑 OR。tombstone 在显式 ack 前重复 refresh 必须重复返回同一
Invalidated，不因 command response 丢失而降为 BootstrapRequired。ack 必须同时匹配 active invocation、
`prior_request_id` 和当前 `invalidation_id`；旧/重复 ack 遇到已更新 tombstone 时不得消费，而是返回最新
Invalidated。只有当前 ID 的 ack 可消费并返回 BootstrapRequired。

ack response-loss 使用 receipt 保证幂等：若 tombstone 已消费、current 仍空，且重试 ack 同时匹配 active
invocation、prior request 和 receipt invalidation ID，则返回与首次 ack 完全相同的 BootstrapRequired payload；
不递增 revision、不调用 backend、不启动搜索。receipt 保留到成功发布新 ResultSet、invocation ownership 切换或
进程结束。若 ack 后出现新 authoritative transition，则新 tombstone 优先于 receipt；旧 ack 返回最新 Invalidated，
不能被 receipt 吞掉。成功 bootstrap/普通 publish 在原子安装新 ResultSet 时清除 receipt。

`apply_authoritative_transition` 在 current 为空但 receipt 存在时，必须以 `acknowledged_snapshot` 作为 provenance
基线：规范化后的 transition 与 snapshot 完全相同（含 prior generation、backend identity、status/reason、
revision exhausted 和 severity）时维持 receipt，不递增 revision、不创建 tombstone；任一可观察字段变化时按
sticky severity 合并，revision 可用则 checked increment，并创建新 tombstone/新 invalidation ID。receipt 中的
terminal severity 继续生效，普通 rebuilding 不能降级。receipt 始终是不可执行、不可展示的控制状态；新 tombstone
一旦创建即优先于 receipt，新的 current-ID ack 成功后用新 snapshot 替换 receipt。

fingerprint preimage 使用版本化、长度前缀 little-endian 编码，包含 query/category/sort、status、total，以及与
分页完全相同的有序 `EntryKey`、每个组件 identity、size 和 modified FILETIME；排除 query sequence、requestId、
resultId、Query2 reply id 和内存地址。backend 只返回 canonical fingerprint、status 和 authenticated batch，绝不
分配或递增 revision。`ResultRegistry` 的 file-domain `content_revision` high-water 是唯一 owner：初始发布、普通
query/category/sort 发布、changed refresh replace、lifecycle invalidate 各 checked increment 一次；Unchanged
不增。overflow 时原子清空 current、标记 revision exhausted 并永久 fail-closed，不回绕或从 backend 重建计数。

### 5. 查询语义

`QuerySpec` 继续由 Rust 根据前端枚举生成。用户 query 必须经过 literal translator；match path、regex、
match case 和 whole word 固定关闭。类别表达式只能由 Rust 生成：

```rust
pub(crate) fn compile_everything_search(spec: &QuerySpec) -> Result<Vec<u16>, QueryCompileError>;
```

translator 必须对空白、引号、反斜杠、`!|<>()*?:;` 和 Unicode 建立 fixture。Rust 二次
`fold_name(name).contains(folded_query)` 只能作为一致性断言；若发生不一致，整次查询失败闭合，不能用
有限 over-fetch 伪造精确 `total`。

### 6. 安全所有权

安装器写入只读 manifest；除版本、架构和预先审核的 SHA-256 外，还固定 `instanceName`、`serviceName`、
`servicePipeName`、`iniPath`、`databasePath`、`configDirectory` 和 `binaryRelativePath`。普通 fetch 脚本只能
验证 lock，禁止根据刚下载的 artifact 生成或重写 SHA-256。更新 lock 是独立人工评审变更，并同时核对
Authenticode publisher。安装、升级和卸载均先验证 manifest、Service binary path 和受管目录。

首装 `service_owner_sid` 是 elevated NSIS token 的用户 SID，即实际提供 UAC 管理员凭据的账户。标准用户
通过 OTS 输入另一管理员凭据时，owner 是管理员账户，不是桌面标准用户。覆盖升级必须读取并保留 manifest
中的既有 owner SID；受管 INI/DB/config ACL 与 pipe SDDL 都绑定该 owner。首版不支持其他用户共享搜索。
首版也不实现应用内 repair command，故障 UI 只提示重新运行可信发布渠道的已签名安装包。

## 六、明确的 No-Go 条件

- Everything 主程序再分发许可或第三方声明无法确认。
- 不能创建与用户 Everything 完全隔离的 instance、Service、pipe、config 和 DB。
- 普通文本无法安全映射且 `total` 无法保持精确。
- Query2 无法验证 reply HWND、source HWND、`dwData`、实际 request flags 或 sort type。
- LIST2 parser 无法对畸形数据失败闭合。
- 超过 200 个相同时间戳结果时无法得到全局稳定的前 200 项。
- Query2 offset 分页无法通过 overlap sentinel、规范化 EntryKey 和双遍重读检测漂移。
- `ConcurrentMutation`、`TieGroupTooLarge` 或 timeout 会污染/替换当前 ResultSet，或被计入 crash-loop。
- 未变化 refresh 会清空/重建 IDs，变化 refresh 无法在单一提交点原子替换。
- fingerprint 未包含逐组件执行身份或 revision overflow 不能失败闭合。
- authoritative invalidation 无法通过 invocation-scoped tombstone（或等价可信通道）可靠送达仍显示旧结果的前端。
- backend runtime epoch/generation 任一可回绕、重置或在 exhausted 后继续接受旧 action。
- terminal invalidation reason 在同一进程仍会触发 bootstrap、timer、search 或 execute，或可被普通 rebuilding transition 解除。
- unacked tombstone 期间普通 search/new query 仍可调用 backend、分配 ID/revision 或发布 current。
- ack response 丢失后相同 ack 不幂等，或 receipt 缺少完整 snapshot 导致 duplicate/changed transition 无法判定。
- 无法泛化现有逐组件 pinning 并把 handles 保持到 Shell API 返回。
- 活跃 `/find` 无法在有界时间内发现新增、删除或重命名。
- 无法用 Service security descriptor 阻止未授权本地账户枚举文件名。
- 覆盖升级无法验证并保留首装 credential-owner SID 与 INI/DB/config ACL。
- 安装升级可能留下不可识别 Service，或需按进程名模糊清理。
- `/find` 需要在查询时弹 UAC、安装 Service 或修改系统配置。
- 生产切换后仍需长期保留两套索引作为 fallback。
