# Everything 索引启动性能与持久化

## 目标与测量

优化 `/find` 的重复启动成本，保留全盘文件搜索范围、现有私有实例和普通用户运行边界。
2026-10-28 在同一机器、同一 Everything 1.4.1.1032 二进制上，用独立实例和数据库副本测量：

| 场景 | 数据库就绪时间 |
| --- | ---: |
| 四天前的旧数据库，默认线程优先级（前次诊断） | 267 秒 |
| 同一旧数据库，普通线程优先级 | 296.803 秒 |
| 空数据库，默认线程优先级 | 11.612 秒 |
| 正常保存后启动，重新生成受管 INI | 1.136–1.190 秒 |
| 主动保存后强制退出，再启动 | 1.148 秒 |

测量使用实际 NTFS 卷，运行时磁盘变更和系统负载并非固定，因此不能作为精确优先级 A/B 对比。
数据支持“旧索引补处理变更是主要成本，持久化后重启明显更快”，不支持提高优先级或减少搜索范围。
以上是数据库就绪时间，不含整个宿主启动和二进制验证耗时，也不是所有机器的性能保证。

## 决策

使用 Everything 1.4.1 已提供的保存数据库 IPC：`WM_USER / EVERYTHING_IPC_SAVE_DB (407)`。
参考 [官方 SaveDB 文档](https://www.voidtools.com/support/everything/sdk/everything_savedb/)
和官方 SDK `ipc/everything_ipc.h`。该消息请求保存，响应不等于磁盘写入完成。

- Ready 已发布且进程健康检查通过后，请求一次保存；未就绪、能力检查失败时不保存。
- 同一进程每 10 分钟再请求一次，失败也等待下一个周期，不高频重试。
- 请求在 Supervisor 后台线程执行；每次发消息最多等待 1 秒，不持有运行状态锁。
- 只向私有 IPC 窗口且窗口 PID 等于所持进程 PID 的客户端发送。每次重新核对 PID。
- 保存失败不将可搜索的实例变成不可用，也不触发重启；下次正常退出仍沿用原保存路径。
- 进程代次变化重新开始检查点周期。退出期间不启动新的检查点；并发退出最多等待已开始的有界请求。
- 不引入新进程、不修改 Service、全局 Everything、线程优先级、网络设置或用户数据。

## 旧缓存处理

不按文件年龄自动丢弃缓存：离线时间长不一定变更多，强制重建可能反而更慢。
当前仍运行且已经就绪的私有实例可直接保存最新索引，无需重建或重启。
积压严重的旧缓存可在用户完全退出 UiPilot 后备份并重建；这属于一次性恢复，不能冒险替换运行中的数据库。

## 验证

- 定向回归：准备中不保存、Ready 保存一次、周期节流、代次/会话转发、已退出不发送。
- Windows 隔离诊断：发送 407，观察数据库写入，再强制结束自己拥有的诊断进程，确认重启仍快速。
- 构建 Setup 后人工验收：正常使用 `/find`，完全退出再启动，确认搜索正常且无需再次等待几分钟。

验证记录：新增“Ready 后保存”测试在修改前失败，修改后文件搜索模块 75 项测试全部通过。
独立实例实际查询对照各 15 次，无失败；未保存时最大 256 ms、中位数 95 ms，保存期间最大
749 ms、中位数 87 ms（包含命令行客户端进程启动开销）。这是该机器上的样本，不代表更大索引
或较慢磁盘也能保证同样延迟。当前运行的私有实例亦经身份、就绪状态检查后成功请求保存，
并观察到实际数据库写入；未重建或替换运行中的缓存。
